## 怎么选

- 先读候选 Issue、相关的代码、测试和设计文档，弄清每个 Issue 真正要解决的问题，再决定这一批做什么。几个 Issue 有共同目标、会改到同一处时可以合成一批。
- 可以不选的情况只有这几种：
  - 它依赖的 Issue 还没有完成：写 `later=false`，在 `wait_for` 中写依赖的 Issue 编号；依赖都关闭后它会自动回到候选。
  - 本身可以做，只是不放进这一批（与这一批无关、超过数量、与进行中的工作项会改到同一处）：写 `later=true`。
  - 需要改 CI / Kiln 配置或给 AI 的说明等超出授权的内容。
  - 缺少只有人才能提供的输入，而且连设计都无法推进。
- "需要先设计"、"PLAN 没写"、"命名未定"、"取舍不明"、"重构风险大"都**不是**不选的理由：技术设计、命名和取舍是你的工作。缺少外部条件（云项目、凭据、费用）只影响依赖它的真实验证，不影响设计和不依赖它的实现。
- 选了 Issue 时写 `design_first` 和 `design_reason`：
  - 默认 `false`：领取后在同一次执行中先设计、再开发，设计和实现在同一个 PR 中交付。
  - 你判断这一批一个 PR 完成不了时写 `true`：先交付只含设计文档的设计 PR，审计通过并合并后，Kiln 自动开始实现。
  - 由你自己判断。只提醒一点：要改已确认的决定（`AGENTS.md`、`docs/PLAN.md` 中列出的）时，PR 会暂停等人确认，先交设计 PR 可以避免代码白写。
- `plan` 写初步计划：要解决什么、大致怎么做、怎么验证。详细设计在领取之后做。
