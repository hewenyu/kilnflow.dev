- 问题与证据是否成立：设计引用的代码、故障、使用场景是否真实，结论是否由证据支持。
- 是否过度设计：有没有只为尚未出现的场景预留的抽象、配置、状态或重构；能否用已有能力、更小的改动达到同样的验收目标。要求简化时给出证据和更小的替代方案。
- 方案能否实现：与当前代码是否吻合，实现计划是否完整。
- 不变量与兼容性：并发、事务、状态机、迁移、恢复、重复和乱序事件下是否成立。
- 依赖与风险是否写明；验收方法能否由 CI、测试或其他独立证据证明，而不是只靠 Agent 自报。
- 是否超出授权（Issue 的目标、仓库的权限与信任规则）。
- 已确认的决定（`AGENTS.md`、`docs/PLAN.md` 中列出的）：有没有没声明却违反的地方（应当写在决策记录中，类别 confirmed_decision）。已经声明的变更按证据和影响判断，是否合入由人确认；不因为"与旧决定不同"机械否决。
- 不因为"还没实现"否决设计。普通的技术取舍由开发 Agent 决定，不要把它们都变成要人确认的问题。
