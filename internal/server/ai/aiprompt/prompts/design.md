## 设计

### 1. 先反向审视：这一批 Issue 是否过度设计？

- 它们真正要解决的当前问题是什么？哪些要求有实际代码、故障或使用场景作为依据？
- 哪些抽象、配置、状态、扩展点或重构只是为尚未出现的场景预留？
- 能否利用已有能力，用更小的改动达到同样的验收目标？
- 如果不做某项设计，会出现什么可证明的问题？如果做了，又增加哪些复杂度、兼容和维护成本？

给出有依据的判断和最小充分方案，说明保留、简化、延后各项的理由。不要为了显得专业扩大范围，也不要仅凭"可能过度设计"拒绝任务。简化如果改变了原验收目标，在交付报告的 `design.decisions` 中写明（类别 `acceptance`），不能悄悄删掉验收项。

### 2. 四问

> **我想要这个任务的更深版本，而不是更大版本。改写前先回答四个问题：**
>
> 1. 这个领域的顶尖专业人士会做哪些我还没要求的事？
> 2. 他们会从哪些最原始的数据或材料入手？
> 3. 他们会用什么具体方法和工具？
> 4. 除了你和我，还有什么能证明结果是对的？
>
> **然后，根据这些答案重写我的提示词，并照新提示词执行。**

回答基于本仓库和这一批 Issue，落实到原始资料、具体方法和独立证据，不要套话。"更深"是更充分的依据、更清楚的不变量 / 边界 / 失败情形、更可靠的验证，不是更多功能或抽象。重写的是这个任务的任务书（设计文档的一部分），不能改写 Issue 的目标、扩张权限，或者把推测当成已确认的要求。

### 3. 设计文档

按任务复杂度写，简单的任务可以很短，不相关的章节不写。包括：原始问题与证据引用、简化判断、四问的回答和重写后的任务书、选定方案与取舍、不变量与失败情形、影响范围、需要时的兼容 / 迁移 / 恢复、实现计划、能独立检查的验收方法。写在仓库开发说明规定的位置；没有规定时写在本 PR 新增的 Markdown 文档里，并在交付报告的 `design.documents` 中列出路径。

### 4. 有疑问的决定

不用等人确认，自己决定，在交付报告的 `design.decisions` 中记录决策过程（现状和依据、考虑过的方案、选择及理由、影响、复盘时要看什么），设计文档中同样写明。只有改已确认的决定（`AGENTS.md`、`docs/PLAN.md` 中列出的，类别 `confirmed_decision`，`ref` 写编号）会让 PR 暂停等人确认；写明旧约束、拟变更的内容、依据、影响和兼容性。不能修改自己的权限或信任规则。

### 5. 外部输入

真实验证需要、只有人能提供的条件（项目、凭据、费用）写进 `design.external_inputs`（阻塞哪些验收项、恢复的条件）。不要创建收费资源，也不要把没有执行的验证写成通过：缺少条件的验收项做到模拟验证为止。
